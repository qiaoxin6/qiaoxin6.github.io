RAG流程详解

发表于2026-09-11|更新于2026-09-11|AI
|总字数:2.6k|阅读时长:8分钟|浏览量:

① 数据接入 → ② 文档解析 → ③ 切分 → ④ 增强/元数据 → ⑤ 向量化 → ⑥ 索引

⑦ 查询处理 → ⑧ 检索 → ⑨ 重排序 → ⑩ 上下文组装 → ⑪ 生成 → ⑫ 后处理

③ 切分 Chunking:将长文档切成可检索的片段

固定切片 按段落→句子→词的优先级递归切，256–512 tokens + 10–20% overlap 是公认黄金区间；被称为 “生产环境 80% 的选择”
结构感知 不按固定长度或语义距离切，而是利用文档本身的结构（标题、章节、段落、列表、表格、代码块、HTML 标签等）作为天然边界，让每个 chunk 保持结构完整性。 比如 Markdown 按照#/##/### 标题层级切 HTML 优点：便宜缺点：长度不固定
语义切分 不在固定长度处切，而在主题发生变化处切。 1.用正则规则切分为独立句子2.一个句子结合前后几个句子组成buffer并向量化3.计算相邻buffer之间的 余弦 距离4.当余弦距离超过阈值代表语义发生变化，标记为切点5.组装chunk，切点前后的句子为一个chuck优点：chunk 内部主题一致，检索信噪比高缺点：每句都要调 embedding，索引成本是递归切分的 5–10 倍；阈值需按语料调参；chunk 长度不可控适用：主题混杂的长文档，语料规模不大、能接受较高索引成本
父子分层 子块用于检索，父块用于生成先切分父块，再在父块中切子块。 子块embedding入库父块不向量化。 召回子块再所有父块返回。优点：同时解决 “小块检索准” 和 “大块上下文全” 的矛盾；2025–2026 最广泛采用的生产模式缺点：索引和存储有额外开销；实现比单层切分复杂适用：几乎所有需要兼顾检索精度和答案质量的生产 RAG
命题切分 不按文本边界切，而是用 LLM 把内容改写为原子事实，每个事实作为一个 chunk。 优点：检索精度极高，余弦相似度信噪比好；EMNLP 2024 论文验证缺点：LLM 调用成本高、速度慢；chunk 数量暴增；可能丢失事实间的关联适用：高价值、更新慢的静态知识库（法规、FAQ、产品手册）；

④ 增强/元数据

内容增强 ： 用 LLM 或 NLP 工具为 chunk 补充额外文本，这些文本可以拼接到 chunk 前、单独向量化、或建关键词索引。

方法 做什么 用途
Contextual Retrieval（Anthropic） LLM 读取整篇文档 + 当前 chunk，生成 50–100 token 上下文说明（”这段在文档中的位置和作用”），拼接到 chunk 前 解决孤立 chunk 丢失全局语境；降 49% 检索失败率；当前生产标配
Hypothetical Questions（假设性问题） LLM 为每个 chunk 生成 2–3 个 “这个 chunk 能回答什么问题”，将问题单独 embedding 入库 用户 query 与预设问题向量匹配，比 query↔正文匹配更准；适合 FAQ 型查询
Summary（摘要） LLM 生成 1–2 句摘要 可单独向量化检索，也可作为返回预览
Title（标题） LLM 生成 3–8 词简短标题 关键词匹配 + 返回展示
Keywords（关键词） LLM 或 KeyBERT/RAKE 提取 5–8 个领域术语 建 BM25 / 关键词索引，适合精确匹配（产品型号、年份、编号）
Chunk Header（标题路径） 非 LLM，直接将结构解析得到的标题路径拼到 chunk 前（如 “第三章 > 3.2 > 向量检索”） 零成本补充上下文，支持按章节过滤
文本清洗 小写化、拼写纠错、去特殊 Unicode、缩写展开、数字规范化 消除无关差异，提升向量匹配；注意 “not” 等停用词有语义，别乱删

元数据标注

元数据筛选就是在向量检索之前或之后，用结构化条件（权限、时间、来源、类型等）把搜索范围缩小，既提升检索精度，又保证数据安全。生产环境中权限过滤是必须的，时间和来源过滤按业务需要添加。

类别 字段示例 作用
结构元数据 标题路径、章节号、页码、chunk 位置偏移 按章节 / 页码过滤；返回结果定位
来源元数据 文件名、文档 ID、URL、作者、部门 溯源引用；按来源过滤
时间元数据 创建时间、更新时间、生效日期、版本号 time-aware RAG（优先返回最新内容）；增量更新
权限元数据 ACL、密级、可见部门 / 角色 检索时按用户权限过滤，防止越权
内容类型 正文 / 表格 / 代码 / 图片描述 / 列表 / 标题 按类型过滤；表格类 chunk 可特殊处理
语言 zh/en/… 多语言场景过滤
分类标签 文档类型、主题分类、情感标签 按类别筛选；可由 LLM 或规则生成
ID / Hash 文档 ID + chunk 序号或内容 hash 去重、增量更新、引用

⑤ 向量化

分为 Embedding 模型选择 和 编码策略 （真正的 “方法” 差异） 。

Embedding 模型选择 ：选择开源或者闭源的模型

编码策略：

  1. 传统独立编码 ：每个chuck独立embedding，互相看不见
  2. Late Chunking（迟分编码） ：全文过 transformer 得到每个token的向量列表。然后根据切分点分段并求出每段的平均向量， mean pooling（取平均）得到这个chuck的向量。这种方法会让每个chuck都看过全文。

3.多表示索引：对同一段chuck生成不同表示：原文、摘要、假设问题。生成多个向量并建立索引。只要召回任何一个都分会改chuck。

4.稀疏向量： 不同于稠密向量关注语义，稀疏向量负责关键词精确匹配。 有BM25.

⑦ 查询处理

1.query改写：把模糊、口语化的问题改为完整、清晰的问题

2.query扩写：把一个问题拓展为多个不同表述，从不同角度检索召回

  1. HyDE（Hypothetical Document Embeddings ） 假设性答案： 让LLM根据问题生成一个假设性的答案去检索片段。

适合：适用于问题与文档的风格差异大，使用假设性的答案能更好的检索。答案有固定表述

不适合：LLM对该领域不了解或者答案特别开放。

4.子问题拆解： 把复杂的query拆解为多个简单的子问题去检索召回。

原始：”途家2024年北京地区的退款率比2023年高还是低？原因是什么？”

├→ 子问题1：”途家2024年北京地区退款率”

├→ 子问题2：”途家2023年北京地区退款率”

└→ 子问题3：”退款率变化原因分析”

适合：比较型问题（分为a和b）；聚合型问题（要从多个方向汇总信息）

  1. Step-Back Prompting（退一步提问）

根据当前问题生成更宽泛、背景性的问题去检索宏观的知识，同时用原始问题检索。 二者汇总回答问题。

原始：”途家2024年Q3北京退款率环比变化原因？”

Step-back 问题：”影响住宿平台退款率的常见因素有哪些？”

→ 检索到：季节性、政策变化、疫情、节假日…

原始问题：

→ 检索到：Q3 具体数据和报告 → 综合回答

6.路由查询

意图理解查询问题，路由到不用的处理链路

类型 特征 检索策略
事实型 “X 是什么” 小块、精确匹配、top-k 小
摘要型 “总结一下 X” 大块 / 父块、top-k 大
比较型 “A 和 B 的区别” 子问题分解，多路检索
操作型 “怎么做 X” 路由到手册 / FAQ
数据型 “X 的数量 / 比例” 路由到数据库，Text-to-SQL

⑧ 检索

按检索机制分 ：

1.稠密检索：query 和 chunk 都转成 embedding 向量，用余弦相似度或点积找最近邻。

  • 优点：能匹配语义相近但字面不同的内容（”怎么退钱”→”退款流程”）
  • 缺点：对精确关键词（型号、编号、数字）不敏感；可能 “语义跑偏”

2.稀疏检索： 基于词项匹配 ，关键词检索

  • 优点：精确匹配专有名词、型号、日期；可解释
  • 缺点：无法理解同义 / 近义

​ 3.混合检索：稠密 + 稀疏，然后RRF融合排序

RRF

混合检索时稠密检索和BM25的分数体系不一样，稠密检索得到的是0-1的相似度，BM25是无界的词频。RRF的思想是只看排名不看分数。

公式：RRF(d) = Σ 1 / (k + rank_i(d))

k为平滑常数，通常取60，目的是降低头部排名的权重差距，避免第一名和第二名分差过大

没出现在某路结果中的文档，该路贡献为 0

⑨ 重排序

​ 检索阶段追求快，从大量的文档中检索出几十条chuck，但不保证准确。

​ 重排序对几十条chuck做精排，速度慢但是效果好。用于找到最相关的chuck。

重排序方法：

1.Cross-Encoder（交叉编码器）

把query和chuck拼接起来送入重排序模型让模型打分精排得到topK。

重排序精度高但是速度慢

2.LLM 重排序

使用大模型来判断相关性，速度慢、贵，但是质量高，能理解复杂语义

  1. 基于规则 / 元数据的重排

根据时间、来源、标签设计不同的权重，一般用来辅助排序
